# 管理面板架构检查与后续拆分计划

日期：2026-06-17

## 本轮已修复

### 1. AI 题库页概览过载

原问题：概览页同时展示统计、蓝图、真题画像、候选审核、质量治理、错因补救、已发布题库和台账，用户很难判断当前页面的主任务。

调整后：

- 概览页保留总览指标。
- 概览页保留「蓝图与知识点」。
- 「真题画像」放在蓝图与知识点之后。
- 候选审核、质量治理、错因补救、已发布题库、题库台账回到独立标签页。

### 2. AI 题库页加载不再整页失败

原问题：一个后台模块 500，就可能导致 AI 题库管理页整体无法加载。

调整后：改为分块加载。蓝图、知识点、生成队列、候选题、已发布题库、台账、真题画像、质量、错因等模块独立成功或失败。失败时只提示对应模块，已成功模块仍可操作。

### 3. AI 运维页加载不再整页失败

原问题：AI 观测、Provider、生成队列、训练事件、发布证据混在一个请求组里。

调整后：改为分块加载。某个运维模块失败时，不影响其它模块展示。

### 4. 大纲治理页加载不再整页失败

原问题：大纲治理、导入记录、待复核题目任何一个失败，页面整体进入错误状态。

调整后：三块独立加载。比如导入记录暂时失败时，仍能查看治理概览和待复核题。

### 5. 审计页加载不再整页失败

原问题：审计页一次加载 24 个模块，包括用户审计、练习汇总、AI 运维、题库治理、质量治理、训练观测。任意一个失败都会拖垮整页。

调整后：24 个模块改为分块容错。页面提示失败模块名称，已加载模块继续可用。

## 仍然存在的架构问题

### 1. 管理页职责仍然偏大

`AdminAuditPage` 和 `AdminAIQuestionBankPage` 仍然承担太多职责。虽然加载容错已改善，但代码仍不利于维护。

建议拆分：

- `QuestionCoveragePanel`
- `SourceReferencePanel`
- `QualityGovernancePanel`
- `RemediationPanel`
- `AIOperationsPanel`

### 2. 数据加载还不是完全按标签懒加载

当前已经避免整页失败，但部分页面仍会一次请求很多模块。更成熟的方案是：

- 当前标签页只加载当前标签需要的数据。
- 概览页只加载概览所需的轻量摘要。
- 进入候选审核、真题画像、质量治理等标签时再加载明细。
- 批量操作完成后只刷新相关模块。

### 3. 长任务状态仍应继续统一

生成蓝图、生成候选、AI 映射、批量发布、画像生成都属于长任务。现在已有一些进度提示，但还应统一为同一种状态模型：

- queued：已排队
- running：处理中
- succeeded：成功
- partial_failed：部分失败
- failed：失败
- cancelled：取消或中断

每个长任务都应显示：当前处理对象、已完成数、失败数、下一步动作。

### 4. 页面层仍有过多业务判断

现在不少门禁、状态、批量筛选逻辑还散在页面组件中。后续应沉到前端 domain helper 或后端返回的 action model：

- 是否可发布
- 是否可批量发布
- 是否需要人工确认
- 是否建议重生
- 是否允许进入训练

页面只负责渲染状态和触发动作。

### 5. 真题画像应成为题库生产链路的独立阶段

目前位置已经调整到「蓝图与知识点」之后，但更完整的链路应是：

1. 大纲导入与治理
2. 蓝图与知识点覆盖
3. 真题导入与画像
4. 风格标准沉淀
5. 生成候选题
6. AI 审题门禁
7. 人工抽检或人工确认
8. 发布入库

### 6. P0：全页刷新仍会干扰局部动作反馈

当前候选翻页、真题样本翻页、台账翻页和部分筛选变化仍会触发整页数据刷新。虽然分块加载避免了整页白屏，但用户仍可能看到按钮反馈被下一次加载覆盖，或者误以为长任务切页后中断。

可执行方案：

- 把 `AdminAIQuestionBankPage` 的大 `useEffect` 拆成按工作区加载的 hooks。
- 候选审核、真题画像、质量治理、错因补救、台账分别维护 `loading/error/lastUpdated`。
- 批量动作完成后只刷新相关模块，比如候选发布只刷新候选队列、已发布题库和台账，不重新拉质量/错因/真题画像。

### 7. P0：长任务与即时动作仍需要统一状态模型

批量生成蓝图、补齐候选、追加候选、AI 映射、批量发布和画像生成都属于长任务。现在有局部进度，但 `runAction` 仍把部分“已排队”动作显示为“已完成”，这会造成“没有反应”或“是不是中断了”的错觉。

可执行方案：

- 前端统一 `ActionState`：`queued`、`running`、`succeeded`、`partial_failed`、`failed`、`cancelled`。
- 后端长任务返回 job id、目标对象、当前状态、下一步动作。
- 蓝图/候选/生成队列统一展示同一 job 状态，而不是把队列列表和知识点卡片割裂展示。
- 所有按钮使用同一套进行中文案和局部 spinner，不再只灰掉按钮。

### 8. P0：门禁通过、人工确认和人工覆盖语义仍需拆开

候选题现在会展示“门禁通过”“需要人工确认”“建议重生”等状态，但批量发布按钮仍容易让用户误解为所有门禁通过题都已经完成最终人工审核。

可执行方案：

- 后端为每道候选返回明确 action model：`canPublish`、`requiresHumanConfirmation`、`requiresOverrideReason`、`publishBlockedReasons`。
- 前端拆成两个发布动作：“发布门禁通过题”和“人工确认后发布”。
- 人工确认发布必须弹出确认或填写 note，写入审计记录。
- 批量发布结果要展示成功、跳过、失败以及跳过原因。

### 9. P1：真题画像对蓝图和扩题策略的反哺还不完整

当前 active 真题画像会进入生成 prompt，并做相似度门禁；但真题映射的 topic 分布还没有反哺蓝图覆盖、题型比例、难度分布和扩题优先级。

可执行方案：

- 新增真题 topic distribution：按 `topicId/topicCode` 聚合真题频次、难度、题型、认知技能和选项模式。
- 在蓝图健康中展示“真题覆盖热度”和“缺蓝图/缺候选/真题高频但题库不足”。
- 批量补蓝图和追加候选优先处理真题高频但题库不足的知识点。
- 生成候选时同时参考 subject profile 和 topic distribution。

### 10. P1：真题 PDF/截图到 JSON 仍在人工链路外

当前 AI 题库页支持粘贴或上传 JSON，但没有在本页直接完成“PDF/截图 -> JSON 草稿”的能力。用户仍需要先让外部流程或我们手工转换，再上传 JSON。

可执行方案：

- 新增 `source-documents/parse-upload`：接收 PDF/图片，执行 OCR/LLM 解析，产出同 `sourceReferenceTemplate` 兼容的 JSON 草稿。
- 前端保留“上传 JSON”作为稳定入口，同时新增“上传 PDF/图片生成 JSON 草稿”。
- 所有解析结果先进入草稿，不直接入画像；仍走现有 JSON 校验、导入、AI 映射和人工确认链路。

### 11. P1：顶部统计和状态筛选口径仍需收敛

部分顶部统计来自当前页数据，状态筛选在候选、已发布题库和台账里含义不同。用户看到数字变化时不容易判断是全局变化、当前页变化，还是当前筛选变化。

可执行方案：

- 顶部摘要只使用后端全局 summary；如果只能拿当前页数据，文案必须标注“本页”。
- 候选状态筛选、正式题状态筛选和台账状态筛选拆开，不再共享同一个 `status`。
- 所有列表标题显示：总数、当前页范围、当前筛选条件、批量动作范围。

### 12. P0 落地：候选题和真题画像动作已接入局部刷新

本轮已把 `runAction` 从“成功后一律全页刷新”改成可配置刷新策略：默认仍保留全量刷新以兼容未拆模块，但高频动作可以指定局部刷新或禁止重复刷新。

- 组织成员批量导入后的“复制全部邀请链接”补齐剪贴板失败反馈；浏览器拒绝 clipboard 时，会提示下载 CSV 或手动复制，而不是点击后无反应。

- 后续还应继续把耗时超过 3 秒、影响多条数据、或需要跨分页处理的动作迁入后台任务中心；本轮解决的是“成功/失败反馈语义”，不是长任务架构的最终形态。
