# 机构管理员 MVP 权限收口方案

日期：2026-06-17

## 背景

当前机构治理能力已经覆盖机构创建、分组、邀请、成员导入、机构 AI 额度池、机构 BYOK/provider 配置和治理日志。现有代码与早期设计中预留了 `owner`、`admin`、`teacher`、`coach`、`viewer`、`student` 等角色，但从当前产品阶段看，这套角色过细，会增加学校端使用成本、权限解释成本和后台维护成本。

MVP 阶段的目标不是一次性建完整 RBAC，而是先让学校或机构能顺利完成核心流程：

- 学校拿到一个机构管理账号。
- 学校能邀请学生、分组、管理成员。
- 学校能配置或由平台代配置机构 AI 额度和 BYOK。
- 学生加入机构后使用机构额度和练习能力。
- 平台内部仍能总览和兜底管理所有机构。

因此，MVP 建议把学校端权限收口为三类账号。

## 当前缺口

平台管理员已经存在，并且 `/admin/organizations` 已经能完成机构、成员、邀请、额度池和 BYOK/provider 的平台侧管理。

当前真正缺的是“机构管理员”闭环：

- 登录身份：学校负责人账号现在只是普通用户或平台 admin，缺少“我是某个机构管理员”的产品入口。
- 权限范围：现有机构管理 API 基本使用平台 `RequiredAdminGuard`，机构成员即使 role 是 `admin`，也不能调用这些后台接口。
- 页面入口：现有 `/admin/organizations` 是平台后台视角，会列出所有机构，不适合直接开放给学校。
- 数据作用域：学校账号需要被限制在自己的 `organizationId` 下，只能管理本机构成员、分组、邀请、额度和 provider。
- 交付流程：平台 admin 创建机构后，还需要把某个用户绑定为该机构 admin，并让这个用户进入学校端机构控制台。

所以后续工程重点不是再增加平台后台能力，而是补齐：

1. 机构管理员身份判断。
2. 机构级 scoped API。
3. 学校端机构控制台。
4. 平台 admin 给用户授权为机构 admin 的操作入口。

## MVP 角色模型

### 1. 平台 admin

平台内部使用，不对学校开放。

职责：

- 创建、编辑、归档任意机构。
- 给机构创建或绑定机构管理员账号。
- 查看所有机构成员、邀请、额度池、provider 配置和治理日志。
- 代学校配置 BYOK/API Key。
- 处理异常邀请、误入组、额度争议和审计排查。

边界：

- 平台 admin 是全局权限，不能作为学校日常使用账号发给校方。
- 所有涉及 API Key、额度、成员批量变更的操作必须写审计日志。

### 2. 机构 admin

学校或代理机构使用的管理账号。MVP 阶段对外统一叫“机构管理员”。当前落地先以底层 `owner/admin` 作为可管理机构的账号；`teacher/coach` 是否也合并为管理员，需要在真实学校交付中确认后再做权限迁移。

职责：

- 管理本机构基础信息中允许学校自助维护的部分。
- 创建和管理分组/班级。
- 生成邀请链接，包含指定邮箱邀请和通用邀请。
- 批量导入学生邮箱并生成邀请。
- 查看、停用、启用、归档本机构成员。
- 查看本机构邀请历史和治理日志。
- 配置机构 AI 额度池和单人每日上限。
- 配置机构 BYOK/provider/API Key。当前更敏感，仍按底层 `manage_provider` 能力控制。

边界：

- 只能访问自己所属机构。
- 不能查看或修改其他机构。
- 不能创建平台级 admin。
- 不能访问平台全局审计、全局用户库、全局 AI 题库治理队列，除非后续单独授权。

### 3. student

学生账号。

职责：

- 通过邀请链接加入机构。
- 使用机构分配的学习、练习和 AI Coach 能力。
- 查看自己的训练记录、错题、学习数据和额度提示。

边界：

- 不能访问机构管理页。
- 不能查看同机构其他学生数据。
- 不能配置额度池、BYOK、邀请和成员。

## 为什么 MVP 不拆 owner/admin/teacher

当前阶段拆分过细会带来不必要复杂度：

- 学校用户很难理解 owner、admin、teacher、coach 的差异。
- 前端要做更多入口和按钮级权限判断。
- 后端要维护更复杂的权限矩阵和测试。
- 客服和交付需要解释“为什么这个老师能发邀请但不能改 Key”。
- 真实学校采购、教务、IT 是否需要分权还没有被验证。

MVP 更应该先验证：

- 学校是否愿意自己维护学生邀请和分组。
- 学校是否真的会自己填 BYOK，还是更倾向平台代配置。
- 学校是否有多人共同管理机构的需求。
- 是否出现“老师能管班级但不能看 API Key”的真实诉求。

在这些需求出现之前，统一的“机构管理员”更清楚。

## 产品形态建议

### 平台后台

保留现有 `/admin/organizations` 作为平台内部后台。

它可以继续展示完整能力：

- 创建或选择机构。
- 分组与邀请。
- 成员管理。
- AI 额度池。
- Provider/BYOK。
- 治理日志。

但这个页面不应直接开放给学校普通管理账号，除非路由和 API 已经做了 organization scope 限制。

### 学校端机构控制台

已新增一个学校端入口：

- `/organization`

学校端只展示当前账号所属机构，不提供“创建或选择机构”的全局列表。

推荐一级导航：

- 概览
- 学生与分组
- 邀请
- AI 额度
- AI Provider
- 操作日志

对学校端文案统一使用：

- “机构管理员”
- “学生”
- “团队 AI 额度”
- “学校 AI Key / Provider 配置”

不要在页面上暴露 owner、teacher、coach 等角色词。

## 权限映射策略

为了兼容现有数据模型，短期不需要立刻删掉底层角色字段。可以做展示和权限映射收口。

### 对外展示

| 底层 role | MVP 展示 |
| --- | --- |
| owner | 机构管理员 |
| admin | 机构管理员 |
| teacher | 待定，默认不进入机构管理 |
| coach | 待定，默认不进入机构管理 |
| viewer | 机构管理员或只读观察员，MVP 可暂不开放 |
| student | 学生 |

### 权限判断

MVP 可先定义两个能力集合：

| 能力 | 平台 admin | 机构 admin | student |
| --- | --- | --- | --- |
| 管理所有机构 | 是 | 否 | 否 |
| 管理本机构成员 | 是 | 是 | 否 |
| 创建分组 | 是 | 是 | 否 |
| 生成邀请 | 是 | 是 | 否 |
| 导入学生 | 是 | 是 | 否 |
| 配置机构额度池 | 是 | 是 | 否 |
| 配置机构 BYOK | 是 | 是 | 否 |
| 查看本机构治理日志 | 是 | 是 | 否 |
| 使用机构 AI 额度 | 可选 | 可选 | 是 |

当前更稳妥的落地方式是先把 `owner/admin` 视为机构管理能力，`student` 只视为学习使用能力。`teacher/coach` 对外可以继续不展示，等真实学校提出“老师也要管理学生/分组”后，再做一次明确的数据迁移或能力开关。

## 账号开通流程

### 平台代开通学校

1. 平台 admin 创建机构。
2. 平台 admin 创建或确认学校负责人用户账号。
3. 平台 admin 将该用户加入机构，角色设为 `admin`。
4. 平台 admin 发送登录方式或邀请链接给学校负责人。
5. 学校负责人登录后进入机构控制台。
6. 学校负责人创建分组、生成邀请或导入学生。

### 学生加入机构

1. 机构 admin 生成指定邮箱邀请或通用邀请。
2. 学生打开 `/organizations/invite?token=...`。
3. 未登录则先登录或注册。
4. 系统校验邀请状态、邮箱绑定、过期时间、使用次数。
5. 学生加入机构，成为 `student`。
6. 后续做题相关 AI 优先使用机构额度池和机构 provider。

## 邀请规则建议

为了减少运营混乱：

- 同一机构、同一邮箱、同一分组、同一角色下，只允许存在一个有效 pending 邀请。
- 需要重新发链接时，使用“重新生成”，新链接生成后旧链接归档。
- 通用邀请也应避免同一机构同一分组重复生成多个有效链接。
- 邀请历史不显示旧 token 明文，只显示状态；链接丢失时重新生成。
- 指定邮箱邀请默认 `maxUses = 1`。
- 通用邀请默认 `maxUses = 50`，可后续提供上限配置。

## BYOK 与额度策略

MVP 可以支持两种交付方式。

### 平台托管

平台提供统一 provider，学校只购买或获得机构额度池。

适用：

- 大多数学校试点。
- 不想处理 API Key 的客户。
- 需要平台快速交付和统一质量控制的场景。

### 学校 BYOK

学校提供自己的 provider/API Key，平台或机构 admin 填入机构配置。

适用：

- 大客户。
- 对数据、成本、模型账号有明确要求的学校。
- 已经有自己的 OpenAI-compatible 服务或代理服务。

MVP 注意事项：

- API Key 只写入加密存储，不回显。
- 更新 Key 时只允许覆盖，不允许查看旧 Key。
- Provider 配置失败时，学生端应降级到标准解析或平台 fallback，不能阻断做题。
- 机构 BYOK 是否启用应在机构概览中清楚显示。

## 后续拆分条件

只有出现真实需求时，再把机构 admin 拆成更细角色。

建议触发条件：

- 学校明确要求“老师可管学生，但不能配置 API Key”。
- 一个机构有多个校区、多个班主任，需要按分组隔离成员数据。
- 财务/IT/教务角色需要分离。
- 合同或合规要求 API Key、额度、成员管理分权。
- 学校需要只读观察员查看学习报告。

届时可拆为：

- `owner`：机构最终负责人，管理管理员、额度、BYOK、账单。
- `admin`：日常教务管理员，管理成员、分组、邀请。
- `teacher`：只管理自己分组/班级。
- `viewer`：只读查看报告。
- `student`：学习使用。

## 实施建议

### 第一阶段：权限收口

- 前端学校端只展示“机构管理员”和“学生”。
- 机构页角色下拉去掉 owner/teacher/coach，或暂时只展示 admin/student。
- 后端兼容旧 role，但本次先使用现有能力矩阵：`owner/admin` 可进入机构运营管理，`owner` 可继续管理 provider；`teacher/coach` 暂不直接提权。
- 文案统一，不再给学校用户解释细角色。

### 第二阶段：学校端控制台

- 已从平台后台复用出 scoped organization console。
- API 已增加“当前用户所属机构”查询和机构级能力校验。
- 学校 admin 登录后只能看到自己的机构。
- 平台 admin 继续使用 `/admin/organizations`。

建议最小 API 面：

- `GET /api/v1/organization/me/organizations`：返回当前用户可管理的机构列表和默认机构。
- `POST /api/v1/organization/me/cohorts`：创建或更新本机构分组。
- `POST /api/v1/organization/me/invites`：生成本机构邀请。
- `GET /api/v1/organization/me/invites`：查看本机构邀请历史。
- `PATCH /api/v1/organization/me/invites/:inviteId/archive`：归档邀请。
- `POST /api/v1/organization/me/invites/:inviteId/reissue`：重新生成单个邀请。
- `POST /api/v1/organization/me/invites/bulk-reissue`：批量重新生成邀请。
- `POST /api/v1/organization/me/members`：更新本机构成员。
- `POST /api/v1/organization/me/members/bulk`：批量更新本机构成员。
- `POST /api/v1/organization/me/member-imports/preview`：预检学生导入。
- `POST /api/v1/organization/me/member-imports/apply`：导入学生或生成邀请。
- `POST /api/v1/organization/me/credit-pool`：保存本机构额度池。
- `POST /api/v1/organization/me/provider-configs`：保存本机构 provider/BYOK。

这些接口内部不接收任意 `organizationId`，而是根据当前登录用户的机构成员关系解析可管理机构，避免学校账号越权访问其他机构。

### 第三阶段：高级分权

- 根据真实客户需求，再开放 owner/teacher/viewer。
- 添加分组级数据权限。
- BYOK 和额度操作增加二次确认、操作审计和必要的通知。

## 验收标准

- 学校管理账号不能看到其他机构。
- 学校管理账号可以完成分组、邀请、导入学生、成员管理。
- 学生接受邀请后只能以 student 身份加入机构。
- 同邮箱有效邀请不会被重复创建。
- 重新生成邀请会使旧 pending 链接失效或归档。
- 机构 admin 可配置机构额度和 BYOK，但 API Key 不回显。
- 所有成员、邀请、额度、provider 变更都可在治理日志中追溯。

## 当前产品决策

MVP 不对学校端暴露 owner/admin/teacher/coach 的细分。对外只说：

- 平台管理员
- 机构管理员
- 学生

底层角色字段保留为未来扩展点，但前端、文案和交付流程先按三类账号设计。
