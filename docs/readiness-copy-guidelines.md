# Readiness 文案降复杂度指南

> 日期：2026-06-10  
> 范围：个人页备考准备度、复盘闭环、推荐动作、Admin readiness 发布证据  
> 目标：把内部模型语言翻译成学生能马上理解的下一步行动。

## 1. 核心原则

普通用户不需要理解模型结构，只需要理解三件事：

- 我现在离稳定上考场还有多远。
- 为什么系统这么判断。
- 下一步做什么最有用。

用户侧优先使用“准备度、判断依据、系统把握、下一步、薄弱点、复盘验证”等词；避免直接暴露“成熟度、置信度、证据充分度、校准、阈值、expectedGain、ability lift、sampled”等内部词。

Admin/Ops 可以在下载的 JSON、脚本和 runbook 中保留专业术语；后台页面本身应优先使用“发布判断语言”，让运营能直接判断是否可发布、为什么阻断、下一步处理什么。

## 2. 推荐替换表

| 内部/复杂表述 | 用户侧建议表述 | 说明 |
| --- | --- | --- |
| 备考成熟度 | 备考准备度 | “成熟”抽象，“准备”更贴近考试语境。 |
| 置信度 | 系统把握 | 用户更容易理解“系统有多确定”。 |
| 证据充分度 | 判断依据 | 不让用户感觉自己被“取证”。 |
| expectedGain / 预计提升 | 对准备度帮助 +N | 说明不是分数承诺。 |
| 能力改善率 | 建议有效率 | 更像产品反馈，不像统计口径。 |
| 跟进率 | 按建议完成 | 动作更直观。 |
| readiness | 准备度 | 除 API/脚本外，界面尽量不用英文。 |
| 中高难独立样本 | 中高难题练得还不够 | 解释结果，不暴露统计口径。 |
| 难度 topic 信号 | 不展示或改成“不同难度练习记录” | topic/signal 不适合学生侧。 |
| calibration / 校准 | 建议效果 / 后台调优 | 页面用“建议效果”，runbook/API 可保留 calibration。 |
| threshold / 阈值 | 发布门槛/判断门槛 | 学生侧不展示，Admin 页面用“门槛”。 |

## 3. 个人页表达结构

建议每个 readiness 区块按这个顺序表达：

1. 状态：例如“还在建立判断依据”“正在补基础”“接近稳定”。
2. 原因：一句话说明主要短板。
3. 分数解释：明确“不是模考分数”。
4. 系统把握：低把握时提醒“先用来决定下一步，不代表最终水平”。
5. 下一步：给出一个主行动，其他动作只作为辅助。

示例：

```text
备考准备度 43/100
这不是模考分数。系统会综合做题记录、知识覆盖、难度、模考和复盘，估算你离稳定上考场还有多远。

系统把握较低
现在做题记录还不够，先用这个分数决定下一步，不要把它当最终水平。

下一步：先补齐诊断
```

## 4. 复盘按钮表达

“复盘完成”容易让用户以为点一下就结束了。更准确的用户心智是：

- 已看懂：用户已经复盘过。
- 用同类题验证：系统确认这个错因是否真的修复。
- 已修复：同类题验证通过。

后续 UI 可以把按钮从“复盘完成”升级为：

- `已复盘，去验证`
- `用同类题验证`
- `标记已看懂`

如果当前流程仍是按钮点击完成，则旁边必须解释：“点完后系统会安排同类题验证，不是直接判定已经掌握。”

## 5. Admin/Ops 表达边界

Admin Audit 页面应优先使用：

- 准备度建议
- 建议效果健康
- 准备度判断依据
- 中高难练习门槛
- 准备度门槛发布检查
- 准备度发布记录

下面这些词只建议出现在开发文档、环境变量、脚本输出或下载的 JSON 中：

- calibration
- sampled threshold
- rollout checklist
- evidence JSON
- impacted user-subject count

面向运营人员时，卡片副文案应保留业务解释：

- “建议效果健康”：推荐动作是否有足够真实跟进和有效改进记录。
- “准备度门槛”：用真实用户分布来调整中高难题练习门槛。
- “影响用户”：切换 sampled 后，会改变多少用户-学科的 ready 判断。
- “发布记录”：上线前、上线后和回滚阶段留档，方便审批和复盘。
